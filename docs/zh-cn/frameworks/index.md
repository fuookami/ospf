# 从业务场景选择框架

业务框架把可复用的领域模型、约束、候选生成和求解编排组合起来。你提供业务数据、选择目标并接入求解器，不必从决策变量开始重写整个模型。

这条学习路线与[从 Core 开始建模](/zh-cn/guide/getting-started)并行：已有合适的领域框架时先复用；问题超出框架范围时，再组合上下文或自行建模。不要求先读完 DDD 或列生成理论。

## 容易选错的两个地方

### 装箱与下料：看业务语义，不只看维数

BPP 侧重已有物品的放置与装载，CSP 侧重原料加工、产品需求和方案产出。BPP2D 也支持间距、刀缝和余料报告，CSP2D 的定尺模式也具有二维装箱结构，不能简单按“有没有刀缝”选择。

如果你需要解释“这个图案使用几次，生产多少产品，是否允许超产，是否满足设备工艺”，优先考察 CSP；如果重点是“这些物品放在哪块板、哪个箱、什么坐标和朝向”，优先考察 BPP。随后再核对具体能力边界。

### Gantt 与 Network：时间编排和网络决策可以组合

Gantt 负责全局活动、资源、依赖和日历；Network 负责拓扑、流、资源路径和结构。维修人员的作业排程可能需要 Gantt 加 Network 路径子问题，普通活动排程则不必引入 Network。车辆路径属于 Network 的进阶入口，不是学习网络流的前置条件。

## 建议的学习顺序

1. 阅读[环境与运行方式](./setup)，添加领域依赖并选择实际后端或明确的默认启发式。
2. 选择一个框架，先看其输入、输出和不适用范围。
3. 把第一课的示例函数和启动入口放进小型应用，学习构造输入、调用框架和读取结果。
4. 完成教程末尾的一个业务变更练习，同时修改相应验收条件。
5. 阅读[接入自己的业务](./integration)，再进入对应框架的第二课，把需求、目标和规则替换成自己的数据。
6. 需要跨领域组合时，再阅读[综合案例](/zh-cn/examples/framework-examples)或[DDD 架构](/zh-cn/guide/use-ddd-architecture)。

## 怎样判断自己真的学会了？

不以“程序返回成功”为唯一标准。你应能解释：输入的数量和单位是什么、哪些规则是硬约束、优化的是什么、结果是否满足需求，以及结果证明到什么范围。

| 观察到的结果 | 可以得出的结论 | 不能直接得出的结论 |
| --- | --- | --- |
| 输入校验或模型注册通过 | 数据/装配通过对应检查 | 已求解、已有可行方案 |
| mock 回调返回预设解 | 编排和提取路径在该夹具下工作 | 原生求解器找到该解 |
| 独立枚举验证小实例 | 对所枚举的有限问题成立 | 任意规模和连续模型都成立 |
| 最终 MILP 返回整数方案 | 需继续复核业务可行性与报告 | 完整业务问题已证明最优 |
| 受限列池被证明最优 | 当前候选模型最优 | 未生成的方案也不可能改进 |

Kotlin 与 Rust 共用业务解释，但不假设接口或已完成能力完全相同。每课列出各自的真实入口和验证边界；数值验收以该语言的具体用例为准。
