# 从业务场景选择框架

业务框架把可复用的领域模型、约束、候选生成和求解流程组合起来。你提供业务数据、选择目标并接入求解器，不必从决策变量开始重写整个模型。

这条学习路线与[从 Core 开始建模](/zh-cn/guide/getting-started)并行：已有合适的领域框架时先复用；问题超出框架范围时，再组合多个业务框架，或退回 Core 层自行建模。不要求先读完领域驱动设计（DDD）或列生成理论。

## 容易选错的两个地方

### 装箱与下料：看业务语义，不只看维数

- **问“图案复用几次、生产多少量、是否允许超产”选 CSP**：关注原料加工、产品需求、方案产出和设备工艺。
- **问“放进哪个箱、什么坐标和朝向”选 BPP**：关注已有物品的放置与装载。
- 按业务语义核对边界：BPP2D 也支持间距、刀缝和余料报告；CSP2D 的定尺模式也具有二维装箱结构。“有没有刀缝”不能单独决定选型。

### Gantt 与 Network：时间安排和网络决策可以组合

- **问“活动何时执行、占用哪些资源”选 Gantt**：负责活动、资源、依赖和日历。
- **问“流经哪些弧、沿什么路径、如何建设网络”选 Network**：负责拓扑、流、资源路径和结构。
- 需要时再组合：维修人员排程可将 Gantt 与 Network 路径子问题组合；车辆路径是 Network 的进阶入口。

## 建议的学习顺序

1. 阅读[环境与运行方式](./setup)，添加领域依赖并选择实际后端或明确的默认启发式。
2. 选择一个框架，先看其输入、输出和不适用范围。
3. 把第一课的示例函数和启动入口放进小型应用，学习构造输入、调用框架和读取结果。
4. 完成教程末尾的一个业务变更练习，同时修改相应验收条件。
5. 阅读[接入自己的业务](./integration)，再进入对应框架的第二课，把需求、目标和规则替换成自己的数据。
6. 需要跨领域组合时，再阅读[综合案例](/zh-cn/examples/framework-examples)或[领域驱动设计](/zh-cn/guide/use-ddd-architecture)。

## 怎样判断自己真的学会了？

不以“程序返回成功”为唯一标准。你应能解释：输入的数量和单位是什么、哪些规则是硬约束、优化的是什么、结果是否满足需求，以及结果证明到什么范围。

| 观察到的结果 | 可以得出的结论 | 不能直接得出的结论 |
| --- | --- | --- |
| 输入校验或模型注册通过 | 数据或模型配置通过对应检查 | 已求解、已有可行方案 |
| 模拟回调返回预设解 | 求解调用与结果解析在该测试数据下工作正常 | 原生求解器找到该解 |
| 独立枚举验证小实例 | 对所枚举的有限问题成立 | 任意规模和连续模型都成立 |
| 最终 MILP 返回整数方案 | 需继续复核业务可行性与报告 | 完整业务问题已证明最优 |
| 当前候选集合对应的模型被证明最优 | 在这些候选方案中已找到最优选择 | 未生成的方案也不可能改进 |

::: info Kotlin 与 Rust 的接口差异
Kotlin 与 Rust 共用业务解释，但接口与已完成能力并不完全相同。每课列出各自的入口与结果含义；数值复核以该语言的具体示例为准。
:::

## 术语与阅读约定 {#terminology}

同一领域使用固定称呼：BPP1D 用“容器／容器类型”，BPP2D 用“板材／板型”，BPP3D 用“箱体／箱型”；CSP1D 的“切割方案”包含单次产出，CSP2D 的“切割图案”描述一次加工的排布。正文统一用“费用”描述 `cost`；代码中的类名、字段名和参数名保留 API 原名。

| 术语 | 在教程中的含义 |
| --- | --- |
| 候选方案、列 | 候选方案是可以选用的装载或加工组合；在列生成模型中，通常用一个变量及其在约束和目标中的系数表示一个候选方案 |
| 主问题、受限主问题（`RMP`） | 主问题决定选择哪些候选及其使用次数；受限主问题只考虑当前已生成的候选，在列生成过程中通常先求解其线性松弛模型 |
| 线性规划（LP）、混合整数线性规划（MILP） | LP 允许连续变量；MILP 要求部分或全部变量取整数。线性松弛允许原来的整数变量暂时取小数，用于估计目标界限和指导候选搜索 |
| 列生成、定价 | 列生成逐轮加入候选；“定价”是利用主问题反馈搜索可改进目标的候选，不是设置商品售价。具体接口是否使用精确算法，以各课说明为准 |
| 求解后端、适配器 | 后端负责执行求解，例如 SCIP、Gurobi；适配器把框架的模型、配置和结果转换到后端接口 |
| 模型注册 | 将领域对象对应的变量、约束和目标加入求解模型 |
| 启发式求解 | 按规则寻找方案，通常不提供完整问题的最优性证明；仍需检查结果是否满足业务要求 |
| 当前可行解（`incumbent`） | 求解器目前找到的可行解，不一定最优，交给业务系统前仍需复核 |
| 候选完整性（`complete`） | 是否已枚举完当前规则下的全部候选，不等于已经证明整数最优 |
| 目标界限、最优性差距 | 用于判断当前解离已知最优界限还有多远；后端未提供时应标记为“未提供” |
| 结果指标（KPI） | 箱数、利用率、费用、欠产等业务统计，具体字段随框架和语言而不同 |
