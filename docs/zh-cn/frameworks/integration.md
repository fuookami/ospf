# 从业务示例接入自己的应用

完成任意一课后，不必先接入 HTTP 服务。先做一个只依赖业务框架的小型应用：读一份固定输入，完成一次真实调用，输出可以逐项复核的结果。等输入、结果和错误处理稳定后，再接数据库、队列或 UI。

## 1. 从最小调用流程开始

```mermaid
flowchart LR
    A[订单与资源快照] --> B[业务适配与单位校验]
    B --> C[领域问题与配置]
    C --> D[框架及求解后端]
    D --> E[求解状态检查与业务复核]
    E --> F[业务结果与审计记录]
```

各框架的入口与返回类型不同，这不是一个可以直接复制的统一 API。箭头表示应用职责；不要为了统一接口而丢掉原始报告、物理量或错误信息。

| 层次 | 应当放什么 | 不应当放什么 |
| --- | --- | --- |
| 输入适配 | 订单 ID、单位、时间、库存与资源的显式转换 | 隐式补零、静默丢订单、按尺寸合并不同 ID |
| 应用调用 | 领域问题、配置、后端、时限、扩展配置 | 再实现一份框架已有的守恒或重叠公式 |
| 业务规则 | 单个候选方案策略或全局建模扩展 | 只在导出报表时才发现硬约束违反 |
| 结果适配 | 已验证方案、状态、指标、缺口与诊断 | 将模拟结果、空渲染对象或未找到可行解的报告当成业务方案 |

## 2. 从示例到业务应用，依次改五处

1. **保留手算基准**：先运行第一课的业务函数和 `main`，确认数据、后端与结果读取接通；不要先替换成全部生产订单。
2. **确认实际求解方式**：需要原生求解器的示例应配置实际后端；使用默认启发式的示例应如实标明算法。BPP2D/BPP3D 要分别配置受限主问题和最终整数求解的后端，并保留各阶段报告。
3. **处理请求边界错误**：第一课在命令行程序中抛出异常或返回错误，接入服务端时应转换为结构化响应；未找到可行解时保留原始报告。各 API 的外层返回类型并不相同。
4. **一次替换一类数据**：先需求，再资源，最后加规则。保留能手算的小问题，逐项检查件数守恒、库存上限等必须始终满足的业务规则。
5. **最后接基础设施**：加入数据库、队列与 UI；避免过期结果覆盖新请求，诊断日志脱敏，不记录许可证和凭据。

按[环境页](./setup)配置依赖与原生库。第一课源码含完整导入；同名 Kotlin/Rust 构造器不一定可以互换。

## 3. 输入进入模型前要检查什么？

| 输入 | 需要作出的业务决定 |
| --- | --- |
| ID 与引用 | 是否唯一，所有产品、箱型、资源、节点引用是否存在 |
| 数量与单位 | 件/卷是否为整数，长度/重量如何转换，零需求是否保留 |
| 库存与上界 | 未提供是否表示不限；不能把 `null`、零和缺失字段混用 |
| 时间与日历 | 时区、允许起点、执行区间、冻结规则和已实际执行记录 |
| 目标 | 优先箱数、消耗、费用还是服务水平；权重采用什么归一化规则 |
| 预算 | 候选数、节点数、迭代和总时限；预算耗尽后怎样展示现有方案 |

请求取消和求解时限应使用实际后端支持的接口。若只停止等待、后端仍在计算，应明确区分这两种状态，并防止过期结果覆盖新一轮排程。

## 4. 返回成功之后，还要分两层判断

外层调用成功只表示拿到了报告或结果；报告内仍可能是不可行、达到时限但未找到可行解、达到时限且已有可行解，或已证明最优。具体枚举和字段以对应语言源码为准。

| 观察 | 应用应做什么 |
| --- | --- |
| 输入或技术错误 | 返回可定位的错误，不展示旧方案冒充本次成功 |
| 正常终止但无可交付方案 | 展示原因与诊断；区分完整问题不可行和当前候选不足 |
| 已找到可行解 | 先完成业务复核，再按真实求解状态交付；限时不能改成最优 |
| 当前模型被证明最优 | 记录模型范围、候选完整性、额外规则及证明来源 |
| 几何/库存/工艺复核失败 | 不交付，保留输入与原始报告，检查建模或提取路径 |

推荐业务输出至少包含请求/输入版本、采用的配置、实际后端、可交付性、原始求解状态、目标与单位、方案、缺口和诊断。**这是应用层建议，不是 OSPF 保证存在的统一序列化数据结构。** 没有目标界限或最优性差距时写“未提供”，不要补为零。

## 5. 用三组用例保护接入

| 用例组 | 例子 | 验收 |
| --- | --- | --- |
| 可行基准 | 一箱装载、一个图案、两活动、四节点流 | 精确数量、几何/工艺/守恒、资源与重算费用 |
| 刻意不可行 | 单件超长、冻结与停机冲突、共享资源不足 | 不生成伪方案；报告范围正确 |
| 边界与故障 | 重复 ID、错单位、零库存、后端失败、限时无解 | 不静默改输入；技术错误与业务求解状态分开 |

测试时同时检查业务规则和目标值。多个等价最优方案可能使用不同坐标或活动次序；应优先检查件数、库存、资源等要求，以及目标值的允许误差。只有业务确实要求固定顺序时，才限定具体方案。

第二课的手算场景可作为业务验收基准，输入构造和规则示例可用于接入。请用自己的输入和求解后端验证扩展后的完整问题；链接中的源码测试主要用于核对单项能力。
